### 快速修复：提交 Bug 修复

对于简单的 Bug 修复，你可以立即开始：

<Steps>
    <Step title="Reproduce the issue">
        在克隆仓库之前，请确保你能可靠地复现 Bug。这有助于确认问题并提供修复的起点。维护者和其他贡献者应该能够根据你的描述复现问题，而无需额外的设置或修改。
    </Step>

    <Step title="Fork the repository">
        :::python
        将 [LangChain](https://github.com/langchain-ai/langchain)、[LangGraph](https://github.com/langchain-ai/langgraph) 或 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库 fork 到你的 <Tooltip tip="If you fork to an organization account, maintainers will be unable to make edits, which may significantly delay acceptance.">个人 GitHub 账户</Tooltip>
        :::
        :::js
        将 [LangChain](https://github.com/langchain-ai/langchainjs)、[LangGraph](https://github.com/langchain-ai/langgraphjs) 或 [Deep Agents](https://github.com/langchain-ai/deepagentsjs) 仓库 fork 到你的 <Tooltip tip="If you fork to an organization account, maintainers will be unable to make edits, which may significantly delay acceptance">个人 GitHub 账户</Tooltip>
        :::
    </Step>

    <Step title="Clone and setup">
        :::python

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # For instance, for LangChain:
        git clone https://github.com/parrot123/langchain.git
        ```

        <Warning>
            LangChain Python 仓库是一个 **单体仓库** — 仓库根目录下没有 `pyproject.toml`。每个包都有自己的 `libs/`（例如 `libs/core/`、`libs/langchain/`、`libs/partners/openai/`）。在运行 `uv` 命令之前，你必须 `cd` 到相关的包目录。
        </Warning>

        ```bash
        # Navigate into the package you want to work on, then install dependencies
        cd libs/core          # or libs/langchain, libs/partners/openai, etc.
        uv sync --all-groups

        # or, to install a specific group only:
        uv sync --group test
        ```

        如果你之前没有安装 [`uv`](https://docs.astral.sh/uv/)，则需要安装。请参阅 [仓库结构](#仓库结构) 部分以获取所有包及其位置的完整列表。
        :::
        :::js

        ```bash
        git clone https://github.com/your-username/name-of-forked-repo.git

        # For instance, for LangChain:
        git clone https://github.com/parrot123/langchainjs.git

        # For LangGraph:
        git clone https://github.com/parrot123/langgraphjs.git
        ```

        ```bash
        # Inside your repo, install dependencies
        pnpm install
        # Create a build for all packages to resolve workspace dependencies
        pnpm build
        ```
        :::
    </Step>

    <Step title="Create a branch">
        为你的修复创建一个新的分支。这有助于组织你的更改，并使后续提交拉取请求变得更容易。

        ```bash
        git checkout -b your-username/short-bugfix-name
        ```
    </Step>

    <Step title="Write failing tests">
        添加 [单元测试](#测试编写规范)，这些测试在没有你的修复的情况下会失败。这允许我们验证 Bug 是否已解决，并防止回归
    </Step>

    <Step title="Make your changes">
        在遵循我们 [代码质量标准](#代码质量标准) 的情况下修复 Bug。进行 **最小必要的更改** 以解决问题。我们强烈建议贡献者在开始编码之前在问题下评论。例如：

        > *"我想处理这个问题。我的预期方法是 [...简短描述...]。这符合维护者的期望吗？"**

        一句 30 秒的评论通常可以防止如果你最初的方案是错误的情况下浪费精力。
    </Step>

    :::js
    <Step title="Run build">
        运行构建命令以确保包仍然可以正常构建
        ```bash
        pnpm build
        # or build a specific workspace package
        pnpm --filter @langchain/core build
        ```
    </Step>
    :::

    <Step title="Verify the fix">
        确保测试通过且没有引入回归。在提交 PR 之前，请确保本地所有测试都通过

        :::python

        ```bash
        make format
        make lint
        make test

        # For bugfixes involving integrations, also run:
        make integration_tests
        # (You may need to set up API testing credentials)
        ```
        :::
        :::js

        ```bash
        pnpm lint
        pnpm test

        # For bugfixes involving integrations, also run:
        pnpm test:int

        # Or run tests in a specific workspace package
        cd libs/langchain-core
        pnpm test
        pnpm lint

        # Or run tests for a specific package from the root of the repo
        pnpm --filter @langchain/core test
        pnpm --filter @langchain/core lint
        ```
        :::
    </Step>

    <Step title="Document the change">
        如果行为发生变化，请更新 docstrings 和/或行内注释
    </Step>

    <Step title="Submit a pull request">
        遵循提供的 PR 模板。如果适用，使用 [关闭关键词](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)（例如 `Fixes #ISSUE_NUMBER`）引用你正在修复的问题，以便在 PR 合并时自动关闭该问题。
    </Step>
</Steps>

## 贡献指南

在为LangChain项目贡献之前，请花时间思考你贡献的目的。如果你的唯一目标只是为简历添加一个"首次贡献"（或只是寻找快速胜利），你可能更适合参加训练营或在线教程。

为开源项目做贡献需要时间和精力，但也能帮助你成为更好的开发者并学习新技能。不过需要知道，这可能会比参加培训课程更难更慢。但只要愿意投入时间做好每件事，贡献开源项目就值得！

### 向后兼容性

<Warning>
    公共API的破坏性变更仅允许在关键安全修复时进行。

    关于主要版本发布的详细信息，请参见我们的[版本政策](/langchain/oss/versioning)。
</Warning>

通过以下方式保持兼容性：

<AccordionGroup>
    <Accordion title="Stable interfaces">
        **必须始终保留**：

        - 函数签名和参数名称
        - 类接口和方法名称
        - 返回值结构和类型
        - 公共API的导入路径
    </Accordion>

    <Accordion title="Safe changes">
        **可接受修改**：

        :::python
        - 添加新的可选参数
        :::
        :::js
        - 添加新的可选参数/类型参数
        :::
        - 为类添加新方法
        - 不改变行为的前提下优化性能
        - 添加新模块或函数
    </Accordion>

    <Accordion title="Before making changes">
        - **这会破坏现有用户代码吗？**
        - 检查目标是否为公共的
        :::python
        - 如果需要，是否在`__init__.py`中导出？
        :::
        - 是否存在测试中的现有使用模式？
    </Accordion>
</AccordionGroup>

### 新功能

我们致力于保持新功能的准入门槛。通常不接受外部贡献者提出的核心抽象类新功能，除非已有明确需求的问题报告。此规则同样适用于基础设施和依赖项变更。

功能贡献要求包括：

<Steps>
    <Step title="Design discussion">
        在问题报告中描述：

        - 解决的问题
        - 建议的API设计
        - 预期使用模式
    </Step>

    <Step title="Implementation">
        - 遵循现有代码模式
        - 提供完整测试和文档
        - 考虑安全影响
    </Step>

    <Step title="Integration considerations">
        - 与现有功能如何交互？
        - 是否有性能影响？
        - 是否引入新依赖？

        我们会拒绝可能导致安全漏洞或报告的功能。
    </Step>
</Steps>

### 安全指南

<Warning>
    安全至高无上。切勿引入漏洞或危险模式。
</Warning>

安全检查清单：

<AccordionGroup>
    <Accordion title="Input validation">
        - 验证并净化所有用户输入
        - 正确转义模板和查询中的数据
        :::python
        - 用户数据中永不使用`eval()`、`exec()`或`pickle`，这可能导致任意代码执行漏洞
        :::
        :::js
        - 用户数据中永不使用`eval()`，这可能导致任意代码执行漏洞
        :::
    </Accordion>

    <Accordion title="Error handling">
        - 使用特定异常类型
        - 错误信息中不暴露敏感信息
        - 实现正确的资源清理
    </Accordion>

    <Accordion title="Dependencies">
        - 避免添加硬依赖
        - 保持可选依赖最小化
        - 审查第三方包的安全问题
    </Accordion>
</AccordionGroup>

## 开发流程

### 预提交钩子

:::python
[LangChain](https://github.com/langchain-ai/langchain) 和 [Deep Agents](https://github.com/langchain-ai/deepagents) 仓库包含 [pre-commit](https://pre-commit.com/) 钩子，在每次提交前自动运行格式化、代码检查和验证。从仓库根目录安装：

```bash
pip install pre-commit  # or: uv tool install pre-commit
pre-commit install
```

钩子强制要求：
- 禁止直接向受保护分支提交
- YAML和TOML语法验证
- 添加末尾空格和文件末尾修复
- 智能引号和非标准空格规范化
- 按包类型 `make format` 和 `make lint`
:::

### 运行测试

<Info>
    测试目录相对于您工作的包位置
</Info>

我们优先使用单元测试而非集成测试。单元测试在每次拉取请求时运行，因此应快速且可靠。集成测试通过定期调度运行，需要更多环境配置，应保留用于验证与外部服务接口。

#### 单元测试

:::python
**位置**: `tests/unit_tests/`
:::
:::js
**位置**: `src/tests/FILENAME_BEING_TESTED.test.ts`
:::

单元测试覆盖不依赖外部API的模块逻辑。新增逻辑需补充单元测试，并在测试中验证预处理/后处理和模拟外部依赖。

**要求**：
- 禁止网络调用
- 覆盖所有代码路径（含边界情况）
- 使用依赖模拟

运行单元测试：

:::python
```bash
make test

# Or directly:
uv run --group test pytest tests/unit_tests

# To run a specific test:
TEST_FILE=tests/unit_tests/test_imports.py make test
```
:::
:::js
```bash
# Run the entire test suite
pnpm test

# Or run a specific test file
pnpm test src/tests/FILENAME_BEING_TESTED.test.ts

# Or run a specific test function
pnpm test -t "the test that should be run"
```
:::

#### 集成测试

:::python
**位置**: `tests/integration_tests/`
:::
:::js
**位置**: `src/tests/FILENAME_BEING_TESTED.int.test.ts`
:::

集成测试覆盖依赖外部API的逻辑（通常涉及与其他服务集成）。

### 依赖项

LangChain包通过**强依赖**和**可选依赖**区分，以保持包轻量并减少用户安装开销。

<Tabs>  
    <Tab title="Optional dependencies">  
        大部分新依赖都应设置为可选。在以下情况使用可选依赖：  

        - 依赖仅用于特定集成或功能  
        - 用户无需该依赖仍可正常使用包  
        - 依赖体积较大或包含过多传递依赖  

        **要求：**  
        - 未安装该依赖的用户必须能**导入**代码而**无任何副作用**（无警告、无错误、无异常）  
        - `pyproject.toml` 和 `uv.lock` **未修改**  

        **添加可选依赖的步骤：**  
        1. 将依赖添加到测试依赖文件（如 `extended_testing_deps.txt`）  
        2. 编写至少尝试导入新代码的单元测试。理想情况下，测试使用轻量级假数据验证逻辑  
        3. 对需要依赖的单元测试使用 `@pytest.mark.requires("package_name")` 装饰器  

    </Tab>  

    <Tab title="Hard dependencies">  
        硬依赖会在用户安装包时自动安装。仅在以下情况使用硬依赖：  

        - 包**无法正常工作**  
        - 依赖体积小且传递依赖极少  
        - 无合理方式使功能可选项化  

        <Warning>  
            添加硬依赖会增加所有用户的安装时间和潜在版本冲突。  
            维护者会对硬依赖添加进行严格审查！  
        </Warning>  

        **添加硬依赖的步骤：**  
        1. 提交议题或讨论说明为何必须使用硬依赖  
        2. 在 `pyproject.toml` 的适当章节添加依赖  
        3. 运行 `uv lock` 更新锁文件  
        4. 编写覆盖新功能的完整测试
