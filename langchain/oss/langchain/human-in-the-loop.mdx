人机协作（HITL）[中间件](/langchain/oss/langchain/middleware/built-in#人机交互)允许您为智能体工具调用添加人工监督。
当模型提议一个可能需要审核的操作时——例如，写入文件或执行SQL——中间件可以暂停执行并等待决策。

它通过将每个工具调用与可配置的策略进行检查来实现这一点。如果需要干预，中间件会发出一个@[中断]来停止执行。使用LangGraph的[persistence layer](/langchain/oss/langgraph/persistence)保存图状态，因此执行可以安全地暂停并在稍后继续。

然后由人工决策决定下一步的操作：操作可以原样批准（`approve`）、在运行前修改（`edit`）、带有反馈拒绝（`reject`），或直接响应（`respond`）用于"询问用户"风格的工具。

当多个工具调用同时被暂停时，每个操作都需要单独的决策。

在默认的批量模式中，按中断请求中操作的顺序提供决策。在 [per-call mode](#每次工具调用暂停一次)中，每个工具调用都有自己的中断并做出一个决策。

当人类拒绝请求的操作时使用 `reject`。仅当人类作为工具行动时（例如回答一个`ask_user`提示词）才使用 `respond`。不要使用 `respond` 来拒绝有副作用的工具，因为其消息被视为成功的工具结果。

<Tip>
当**编辑**工具参数时，保守地做出修改。对原始参数的重大修改可能导致模型重新评估其方法，并可能多次执行工具或采取意外行动。
</Tip>

## 配置中断

要使用 HITL，在创建智能体时将 [中间件](/langchain/oss/langchain/middleware/built-in#人机交互) 添加到智能体的 `middleware` 列表中。

您通过将工具操作映射到每个操作允许的决策类型来配置它。当工具调用匹配映射中的操作时，中间件将中断执行。

此示例使用默认的批量模式。要为每个工具调用暂停一次，请参阅 [设置中断模式](#设置中断模式)。

:::python
```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware # [!code highlight]
from langgraph.checkpoint.memory import InMemorySaver # [!code highlight]


agent = create_agent(
    model="gpt-5.5",
    tools=[write_file, execute_sql, read_data],
    middleware=[
        HumanInTheLoopMiddleware( # [!code highlight]
            interrupt_on={
                "write_file": True,  # All decisions (approve, edit, reject, respond) allowed
                "execute_sql": {"allowed_decisions": ["approve", "reject"]},  # No editing allowed
                "read_data": False, # Safe operation, no approval needed
            },
            # Prefix for interrupt messages - combined with tool name and args to form the full message
            # e.g., "Tool execution pending approval: execute_sql with query='DELETE FROM...'"
            # Individual tools can override this by specifying a "description" in their interrupt config
            description_prefix="Tool execution pending approval",
        ),
    ],
    # Human-in-the-loop requires checkpointing to handle interrupts.
    # In production, use a persistent checkpointer like AsyncPostgresSaver or MongoDBSaver.
    checkpointer=InMemorySaver(),  # [!code highlight]
)
```
:::

## 条件中断

:::python
默认情况下，`interrupt_on` 中列出的每个工具调用都会暂停以供审核。若仅暂停部分调用，需向工具的 `InterruptOnConfig` 添加一个 `when` 谓词。该谓词接收一个 `ToolCallRequest` 并返回 `True` 以中断或 `False` 以自动批准，从而可以根据工具的参数进行控制。
:::

:::js
默认情况下，`interruptOn` 中列出的每个工具调用都会暂停以供审核。若仅暂停部分调用，需向工具的 `InterruptOnConfig` 添加一个 `when` 谓词。该谓词接收一个 `ToolCallRequest` 并返回 `true` 以中断或 `false` 以自动批准，从而可以根据工具的参数进行控制。
:::

:::python
<Note>
条件中断需要 `langchain>=1.3.3`。
</Note>

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware, ToolCallRequest
from langgraph.checkpoint.memory import InMemorySaver


def writes_outside_workspace(request: ToolCallRequest) -> bool:
    """Pause writes to paths outside the workspace directory."""
    path = request.tool_call["args"].get("path", "")
    return not path.startswith("/workspace/")


def is_write_query(request: ToolCallRequest) -> bool:
    """Pause SQL that isn't a read-only SELECT."""
    query = request.tool_call["args"].get("query", "")
    return not query.lstrip().upper().startswith("SELECT")


agent = create_agent(
    model="gpt-5.5",
    tools=[write_file, execute_sql, read_data],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "write_file": {
                    "allowed_decisions": ["approve", "edit", "reject"],
                    "when": writes_outside_workspace,
                },
                "execute_sql": {
                    "allowed_decisions": ["approve", "reject"],
                    "when": is_write_query,
                },
            },
        ),
    ],
    checkpointer=InMemorySaver(),
)
```

当 `when` 谓词返回 `False` 时，调用不会中断直接执行。当它返回 `True`，或当您省略 `when` 时，调用会像往常一样暂停。计算结果为 `False` 的调用永远不会暂停，因此审核者只会看到需要决策的操作。

智能体恢复时，谓词会再次运行，因此它必须对相同的调用返回相同的结果。如果它在恢复时返回 `False`，则工具会运行且审核者的回答会被忽略，即使是一个 `reject`。在批量模式下，如果只有部分调用的结果发生变化，中间件会抛出 `ValueError`。
:::

:::js
<Note>
条件中断需要 `langchain>=1.4.6`。
</Note>

```typescript
import { createAgent, humanInTheLoopMiddleware } from "langchain";
import type { ToolCallRequest } from "langchain";
import { MemorySaver } from "@langchain/langgraph";

// Pause writes to paths outside the workspace directory.
const writesOutsideWorkspace = (request: ToolCallRequest) =>
  !String(request.toolCall.args.path ?? "").startsWith("/workspace/");

// Pause SQL that isn't a read-only SELECT.
const isWriteQuery = (request: ToolCallRequest) =>
  !String(request.toolCall.args.query ?? "")
    .trimStart()
    .toUpperCase()
    .startsWith("SELECT");

const agent = createAgent({
  model: "gpt-5.5",
  tools: [writeFile, executeSql, readData],
  middleware: [
    humanInTheLoopMiddleware({
      interruptOn: {
        write_file: {
          allowedDecisions: ["approve", "edit", "reject"],
          when: writesOutsideWorkspace,
        },
        execute_sql: {
          allowedDecisions: ["approve", "reject"],
          when: isWriteQuery,
        },
      },
    }),
  ],
  checkpointer: new MemorySaver(),
});
```

当 `when` 谓词返回 `false` 时，调用不会中断直接执行。当它返回 `true`，或当您省略 `when` 时，调用会像往常一样暂停。计算结果为 `false` 的调用永远不会暂停，因此审核者只会看到需要决策的操作。

智能体恢复时，谓词会再次运行，因此它必须对相同的调用返回相同的结果。如果它在恢复时返回 `false`，则工具会运行且审核者的回答会被忽略，即使是一个 `reject`。在批量模式下，如果只有部分调用的结果发生变化，中间件会抛出错误。

## 设置中断模式

中间件以两种模式之一暂停，通过 `interrupt_mode` 设置：

- **`"per_call"`**：每个需要审核的工具调用在启动时都会触发自己的中断。每个中断包含其接受的 [`response_schema`](/langchain/oss/langgraph/interrupts#定义中断响应模式) 的答案。您通过一个以中断 ID 为键的决策来回答它。
- **`"batched"`**（默认）：每个模型回合一个中断列出所有需要审核的调用。您按相同顺序回答一系列决策。

为新智能体使用按调用模式。LangChain 计划在下一个主要版本中将其设为默认模式。有关并排比较和按调用模式解决的问题，请参阅 [人机协作概述](/langchain/oss/concepts/human-in-the-loop)。

<HitlPerCallInvokePy />

每个中断值都有 `type: "tool_approval"`，因此客户端可以将其与其他中断区分开。`tool_call_id`、`name` 和 `args` 字段标识正在审查的调用。

### 读取响应模式

每个中断还携带一个 `response_schema`：一个 JSON 模式，其中包含工具允许的每个决策分支，与决策的 `type` 匹配。`execute_sql` 模式包含 `approve` 和 `reject` 分支。`write_file` 模式包含所有四个。对于允许一个决策的工具，`response_schema` 是该决策的单独模式，没有 `oneOf`。

每个选项卡显示一个 `write_file` 分支、一个与之匹配的答案，以及模型收到的 @[ToolMessage]。为提高可读性，下方的分支就地展开 `$ref` 定义，并省略 `title` 和 `description` 字段。

### 通过 ID 恢复每个调用

使用其 ID 作为键对每个中断做出一个决策：

<HitlPerCallResumePy />

你也可以逐个回答中断。未回答的中断将保持挂起状态，直到收到答案后其工具才会运行。

<Warning>
如果一起发送的多个答案中有一个无效，其他工具可以在其中断仍显示为挂起时运行。再次回答它们会运行这些工具两次。在将它们一起发送之前检查答案是否符合 `response_schema`，或逐个发送。
</Warning>

### 修正无效答案

LangGraph 在保存答案之前会根据中断的 `response_schema` 检查每个答案。无效答案会触发 `ValidationError` 并不保存任何内容，因此你可以向相同的中断 ID 发送修正后的答案。此处，编辑省略了 `content`：

<HitlPerCallInvalidPy />

每个错误都命名了失败的字段，这样你可以将其展示给审查者。对于参数为原始 JSON schema 而不是 Pydantic 模型的工具，`response_schema` 显示参数，但 LangGraph 不会根据它们检查编辑。

### 为每次调用设置审查的中间件顺序

在每次调用模式下，审查在工具调用开始时发生，在工具调用中间件链内部：

- 在工具重试或错误处理中间件（如 @[ToolRetryMiddleware] 和 @[ToolErrorMiddleware]）之前列出 `HumanInTheLoopMiddleware`，以便它包裹它们。否则，重试的调用会再次询问审查者，无效的答案会被重试或作为工具错误返回给模型。
- 当智能体恢复时，`HumanInTheLoopMiddleware` 之前的中间件会再次运行直到暂停，因此它必须在调用其处理程序之前没有副作用。工具只有在答案之后才会运行。
- 一个 [`when` 谓词](#条件中断) 在每次调用开始时运行，因此它接收到的 @[ToolCallRequest] 包含了工具。

## 设置中断模式

中间件以两种模式之一暂停，通过 `interruptMode` 设置：

- **`"per_call"`**：每个需要审核的工具调用在启动时都会触发自己的中断。每个中断包含其接受的 [`response_schema`](/langchain/oss/langgraph/interrupts#定义中断响应模式) 的答案。您通过中断 ID 键回答它一个决策。
- **`"batched"`**（默认）：每个模型回合一个中断，列出所有需要审核的调用。您按相同顺序回答一系列决策。

为新智能体使用按调用模式。LangChain 计划在下一个主要版本中将其设为默认模式。有关并排比较和按调用模式解决的问题，请参阅 [人机协作概述](/langchain/oss/concepts/human-in-the-loop)。

您也可以逐个回答中断。未回答的中断将保持挂起状态，直到收到答案后工具才会运行。

<Warning>
如果同时发送的多个答案中有一个无效，其他答案的工具可以在其中断仍显示为挂起时运行。再次回答它们会运行这些工具两次。在将它们一起发送前检查答案是否符合 `response_schema`，或逐个发送。
</Warning>

### 修正无效答案

LangGraph 在保存答案前会将其与中断的 `response_schema` 进行校验。无效答案会抛出错误且不会保存任何内容，因此你可以向相同的中断 ID 发送修正后的答案。中间件将错误包裹在 `MiddlewareError` 中，其 `cause` 是包含问题列表的 Zod 错误。此处编辑省略了 `content`：

<HitlPerCallInvalidJs />

每个问题都指明了失败的字段，因此你可以将其展示给审阅者。LangGraph 仅对具有 Zod v4 对象模式 schema 的工具进行编辑校验。对于其他工具（如具有 JSON schema 的工具），`response_schema` 接受任何 `args` 对象，工具在运行时检查参数。

### 为每次调用设置中间件顺序

在每次调用模式下，审阅发生在工具调用开始时，在工具调用中间件链内部：

- 在工具重试或错误处理中间件（如 @[toolRetryMiddleware] 和 @[toolErrorMiddleware]）之前列出 `humanInTheLoopMiddleware`，以便将其包裹。否则，重试的调用会再次请求审阅者，无效答案会被重试或作为工具错误返回给模型。
- 当智能体恢复时，`humanInTheLoopMiddleware` 之前的中间件会再次运行直到暂停点，因此它必须在调用其处理器前没有副作用。工具仅在答案之后运行。
- 一个 [`when` 谓词](#条件中断) 在每次调用开始时运行，因此它接收到的 @[ToolCallRequest] 包含了工具。

## 执行生命周期

:::python
中间件定义了一个 `after_model` 钩子，在模型生成响应但任何工具调用执行之前运行：

1. 智能体调用模型生成响应。
2. 中间件检查响应中的工具调用。
3. 如果任何调用需要人工输入，中间件使用 `action_requests` 和 `review_configs` 构建一个 @[HITLRequest] 并调用 @[interrupt]。
4. 智能体等待人工决策。
5. 根据`HITLResponse`决策，中间件执行批准或编辑的调用，为拒绝的调用合成 @[ToolMessage]，将人工回复直接作为 @[ToolMessage] 返回`respond`决策，并恢复执行。
:::

:::js
中间件定义了一个 `afterModel` 钩子，在模型生成响应但任何工具调用执行之前运行：

1. 智能体调用模型生成响应。
2. 中间件检查响应中的工具调用。
3. 如果任何调用需要人工输入，中间件使用 `actionRequests` 和 `reviewConfigs` 构建一个 @[HITLRequest] 并调用 @[interrupt]。
4. 智能体等待人工决策。
5. 根据`HITLResponse`决策，中间件执行批准或编辑的调用，为拒绝的调用合成 @[ToolMessage]，将人工回复直接作为 @[ToolMessage] 返回`respond`决策，并恢复执行。
:::
